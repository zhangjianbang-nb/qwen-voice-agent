二、P0：必须优先解决的问题
1. 全双工打断：取消生成任务，不等于停止 Agent 说话

你当前的设计是：

纯文本
VAD 检测到一句话结束
        │
        ▼
启动生成 Worker
        │
        ├── ASR
        ├── LLM
        ├── TTS
        └── 播放
               │
               ▼
主线程持续检测 VAD
               │
               ▼
检测到用户插话
               │
               ▼
cancel_event.set()

这个设计能够取消那些会主动检查 cancel_event 的任务，但不能保证正在进行的操作会立即停止。

例如：

Python
audio = tts.synthesize(text)

if cancel_event.is_set():
    return

play_audio(audio)  # 阻塞播放

如果用户在 play_audio() 执行期间插话，生成线程可能继续播放剩余的全部音频。

即使你在播放前检查一次取消标志，也解决不了这个问题。

1.1 不要让生成 Worker 直接控制音频播放

建议引入一个独立的 AudioOutputController。

纯文本
                    ┌──────────────────┐
                    │   Agent Worker   │
                    │                  │
                    │ ASR → LLM → TTS  │
                    └────────┬─────────┘
                             │
                      带任务 ID 的音频块
                             │
                             ▼
                    ┌──────────────────┐
                    │ AudioOutput      │
                    │ Controller       │
                    │                  │
                    │ 播放队列          │
                    │ 当前任务 ID       │
                    │ 取消与清空         │
                    └────────┬─────────┘
                             │
                             ▼
                         音频设备

生成 Worker 只负责生成音频，并提交给输出控制器。

输出控制器负责：

接收和缓存音频块。
控制实际播放。
检查当前任务是否仍然有效。
取消指定任务的未播放音频。
在必要时停止或清空设备缓冲区。
防止旧任务的音频在新任务开始后继续播放。

这里最重要的是：播放必须有独立于生成任务的控制路径。

否则，生成线程卡在音频播放调用里时，取消事件就可能失去实际意义。

1.2 播放最好采用分块输出

不要等整段 TTS 音频全部生成完毕后，再一次性播放。

更合适的流程是：

纯文本
LLM 输出文本
    ↓
TTS 生成音频块
    ↓
音频输出队列
    ↓
播放器分块消费
    ↓
音频设备

每个音频块可以携带：

Python
@dataclass(frozen=True)
class AudioChunk:
    task_id: str
    sequence: int
    samples: np.ndarray
    sample_rate: int
    is_final: bool = False

实际项目中，还应该明确声道数、样本格式和必要的时间戳。

分块输出有两个主要好处：

减少首次发声延迟。
取消时只需要处理有限的待播放音频，而不是等待整段音频播放结束。

但要注意：分块并不自动意味着低延迟。 如果底层播放设备已经缓存了数百毫秒甚至更多音频，用户插话后仍然可能听到残留声音。

因此，还需要测量设备缓冲区大小，并验证停止播放的实际效果。

1.3 取消必须同时覆盖生成和播放

建议将一次对话定义为独立的任务：

Python
@dataclass
class TurnContext:
    task_id: str
    cancel_event: threading.Event
    deadline: float
    state: str

这里的 state 需要有明确的状态机约束，而不能随意修改。

例如：

纯文本
LISTENING
    ↓
USER_TURN_READY
    ↓
PROCESSING
    ↓
SPEAKING
    │
    ├── 用户插话 → INTERRUPTING
    │                  ↓
    │               LISTENING
    │
    ├── 正常完成 → LISTENING
    │
    └── 超时或异常 → RECOVERING
                           ↓
                        LISTENING

这只是逻辑状态。实现时还需要明确 PROCESSING 与 SPEAKING 之间的转换，以及打断和正常完成同时发生时谁拥有状态转换权。

建议让唯一的状态协调器负责这些转换，而不是由多个线程分别修改共享状态。

取消操作应当至少完成：

使当前任务失效。
设置取消标志。
取消或中止可取消的 ASR、LLM、TTS 请求。
清除该任务尚未播放的音频。
停止或清空已经提交给音频设备的音频。
丢弃旧任务后续迟到的结果。
保留已经确认有效的用户输入，切换到下一轮。

特别注意第 6 点：即使旧任务无法立即终止，也不能允许它在新任务开始后继续输出。

1.4 使用任务 ID，防止旧任务污染新任务

例如：

纯文本
task-101：Agent 正在回答
task-101：用户插话，任务被取消
task-102：新一轮对话开始
task-101：旧 TTS 请求此时才返回

如果没有任务 ID 校验，task-101 的音频可能进入 task-102 的播放队列。

建议所有异步结果都携带 task_id，在提交到下一阶段前进行校验：

Python
if result.task_id != controller.current_task_id:
    discard(result)

真实实现还需要处理任务切换时的并发竞争，不能只依赖一次检查。

评审结论：你的风险点 a 是真实的，而且应该作为 P0 修复。 不过，解决方案不仅是给播放函数增加取消参数，而是让生成任务和播放任务拥有独立的生命周期。

2. VAD 不能直接承担全双工的全部判决工作

你目前使用：

生成期间，如果 VAD 连续 start_frames 帧判定为语音，就中断 Agent。

这个设计可以作为第一版基线，但它存在两个不同的问题。

问题一：Agent 自己的声音可能被当成用户语音。

问题二：真正的用户插话可能被 VAD 漏检或延迟检测。

这两种错误需要分别处理。

2.1 回声导致的自我打断

假设 Agent 正在播放：

纯文本
Agent：你可以先打开设置，然后……

麦克风采集到扬声器的声音：

纯文本
Mic：你可以先打开设置，然后……

VAD 发现了真实存在的人声，于是触发打断。

但是，VAD 的任务是判断一段音频是否包含语音，并不是判断语音来自用户还是 Agent。

因此，单独调节 VAD 阈值并不能可靠解决这个问题。

2.2 建议引入回声消除和播放参考信号

更完整的信号路径是：

纯文本
TTS 音频
    │
    ├─────────────────→ 播放设备
    │
    └──→ 播放参考信号
                 │
麦克风输入 ──────┤
                 ▼
          回声消除 AEC
                 │
                 ▼
          VAD / 语音检测
                 │
                 ▼
          打断判决器

AEC（Acoustic Echo Cancellation，声学回声消除）利用已知的播放信号，尽可能从麦克风输入中去除扬声器回声。

需要强调的是，AEC 并不是简单地从麦克风音频中减去 TTS 音频。真实设备中存在房间混响、声学路径变化、采样时钟差异以及非线性失真，因此需要适当的自适应滤波或专用音频处理实现。

如果暂时不引入 AEC，可以先采取以下措施：

使用耳机进行开发和测试。
维护播放期间的参考信号。
对与播放内容高度相关的回采信号进行辅助判别。
在 Agent 播放期间采用更严格的打断判据。
通过真实扬声器和麦克风组合测试误打断率。

但不要直接在整个播放期间关闭 VAD。这样虽然能避免部分自我打断，却会使真正的用户插话无法及时触发。

2.3 VAD 应该是打断判决的输入，而不是最终决策者

建议区分以下状态：

纯文本
IDLE
    │
    ▼
LISTENING
    │
    ├── Agent 未播放
    │      └── 常规 VAD 判决
    │
    └── Agent 正在播放
           ├── 回声抑制
           ├── VAD
           ├── 语音持续时间
           ├── 播放状态
           └── 打断判决

打断判决可以先采用连续语音帧阈值、最短语音持续时间和播放状态等条件。

后续再逐步加入 AEC、双讲检测（Double-Talk Detection）等能力。

其中，双讲检测尤其重要：它需要区分只有扬声器回声的情况与扬声器播放和用户说话同时发生的情况。

评审结论：你的风险点 d 成立。全双工系统需要处理回声与双讲问题，不能只依赖一个 VAD 概率阈值。

3. 主线程既做音频采集，又做 VAD，必须避免阻塞

你写的是：

主线程持续读音频帧做 VAD，生成与监听通过线程安全队列解耦。

这里需要明确：主线程到底是不是实时音频线程。

如果主线程执行以下操作：

Python
frame = audio_source.read()

speech_prob = vad.predict(frame)

if speech_prob > threshold:
    ...

那么，只要 read() 阻塞时间不确定，或者 VAD 推理偶尔耗时过长，整个监听循环就可能延迟。

假设音频采样率为 16 kHz，每帧 20 ms：

每帧 320 个采样点。
每秒需要处理 50 帧。
单帧处理时间如果偶尔超过 20 ms，就可能出现积压。
如果连续几帧处理过慢，打断检测和录音切分都可能受到影响。

这里的 20 ms 是示例帧长，不代表所有 VAD 都必须使用这个配置。

推荐架构
纯文本
                 音频输入设备
                       │
                       ▼
              ┌────────────────┐
              │ Capture Thread │
              │ 连续采集音频帧   │
              └────────┬───────┘
                       │
                       ▼
                有界音频队列
                       │
                       ▼
              ┌────────────────┐
              │ VAD / Segmenter │
              │ 语音检测与切分   │
              └────────┬───────┘
                       │
                       ▼
                 Turn Scheduler
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        ASR/LLM/TTS          打断协调器
             │                   │
             └─────────┬─────────┘
                       ▼
               AudioOutputController

不一定需要为每个模块都创建线程，但采集和播放必须具备不被 LLM、ASR、TTS 或记忆 I/O 阻塞的执行路径。

我建议至少将以下职责隔离：

模块	职责	不应执行的操作
Audio Capture	连续采集、添加时间戳	ASR、LLM、磁盘 I/O
VAD / Segmenter	语音检测、切分、前后文保留	等待 LLM 或 TTS
Turn Scheduler	任务调度、取消、状态转换	阻塞等待音频播放完成
Agent Worker	ASR、上下文构建、LLM、TTS	直接阻塞式控制采集
Audio Output	分块播放、清空队列、停止当前任务	等待 LLM 生成完毕
Memory Manager	记忆读写和维护	在实时采集回调中执行同步磁盘操作

如果使用 sounddevice，需要特别注意它的音频回调约束：实时回调不应执行可能长时间阻塞的操作、复杂计算或不可预测的内存分配。

回调可以将音频复制到预分配缓冲区或轻量级有界队列，再交给普通工作线程处理。队列满时必须有明确策略，不能无限等待。

一个容易忽略的细节：有界队列不等于实时队列

如果队列长度允许积压 500 帧，而每帧为 20 ms，那么它可以积累约 10 秒音频。

这时，即使没有丢帧，系统也可能因为处理的是旧音频而失去实时性。

因此需要监控的不仅是队列长度，还有：

音频帧的采集时间。
实际处理时间。
当前队列中最老帧的年龄。
丢帧数量。
端到端延迟。

对于语音识别，不能简单地在所有情况下都丢弃旧音频，因为这可能破坏当前话语。更合理的策略是区分实时检测队列与完整语音片段缓冲区：实时检测链路优先保持新鲜度，录音缓冲区则保留完成 ASR 所需的数据。

4. 取消事件不是超时机制，更不是线程终止机制

这是你当前设计里另一个需要明确的边界。

你提到了：

worker_timeout_s
cancel_event
超时后的取消点

但 Python 的 threading.Event 只能通知线程取消，不能强制终止一个正在执行阻塞调用的线程。

例如：

Python
def worker():
    result = remote_llm.generate(
        prompt,
        timeout=None,
    )

    if cancel_event.is_set():
        return

如果 HTTP 请求永远不返回，线程就永远到不了检查点。

即使设置了 cancel_event，也不会自动中断 HTTP 请求。

同样的问题还可能出现在：

本地模型推理。
TTS 音频生成。
阻塞式音频播放。
网络读取。
等待线程安全队列。
4.1 每个阻塞操作都应该有自己的超时或取消策略

例如：

Python
response = client.post(
    url,
    json=payload,
    timeout=(3.0, 20.0),
)

这里的超时配置只是示例。具体值需要根据服务响应时间、是否流式传输以及业务要求确定。

对于流式 HTTP 请求，还要注意读取超时和总任务截止时间不是一回事：即使每次读取都能及时返回，整个请求仍可能无限延续。

建议同时维护：

连接超时。
读取超时。
单阶段超时。
整轮对话的绝对截止时间。
用户打断时的主动取消机制。
4.2 根据后端的阻塞特性选择隔离方式
后端类型	推荐取消策略	主要限制
HTTP ASR / LLM / TTS	请求超时、关闭响应流、取消请求	远端服务可能仍在执行计算
本地可流式生成后端	停止生成、释放流对象	具体能力取决于推理库
普通阻塞函数	有限超时或专用线程	无法强制安全终止线程
可能永久卡死的第三方代码	进程隔离、监督与重启	需要管理 IPC 和进程生命周期
音频播放	专用输出控制器、设备级停止或清空	设备缓冲区可能存在残留

不要尝试通过随意杀死 Python 线程来解决卡死问题。 这可能让锁、共享数据或外部资源处于不一致状态。

如果需要保证某个后端卡死后不会拖垮整个 Agent，最可靠的边界通常是独立进程，而不是试图强制结束任意线程。

但不必一开始就把所有后端都做成独立进程。先明确每个后端的取消契约，再针对无法可靠取消的后端做隔离。

三、P1：记忆系统与并发安全
5. check_same_thread=False 加锁，并不能自动保证线程安全

你当前的设计是：

Worker 读取 MemoryManager.context_block()，主线程执行 observe()；使用 SQLite check_same_thread=False、锁和 manager 级锁。

这条路线可以成立，但有一个常见误区：

SQLite 连接允许跨线程访问，不代表你的整个记忆系统已经具备一致性保证。

check_same_thread=False 主要是关闭 Python SQLite 对连接线程归属的检查。它不会自动为你的多步骤业务操作建立事务，也不会保证 JSONL 文件、内存缓存和 SQLite 之间保持一致。

5.1 明确共享资源与锁的边界

建议先列出共享状态：

共享资源	可能的并发问题	建议
SQLite 连接	事务交错、连接状态被其他线程影响	专用数据库访问层，明确事务边界
JSONL 文件	多线程交错写入、记录损坏	单写者或专用写入队列
Working Memory	遍历期间增删、TTL 清理竞态	锁内快照，锁外处理
当前对话状态	旧任务覆盖新任务	单一状态协调器与任务 ID
上下文构建	读取到不同时间点的多份数据	定义一致性语义
周期维护任务	与正常读写竞争	维护任务与读写共享明确的同步规则
5.2 不要让全局锁包住整个上下文构建过程

例如：

Python
with self.lock:
    identity = self.load_identity()
    facts = self.load_facts()
    rules = self.load_rules()
    history = self.load_history()
    events = self.load_events()

    return self.assemble_context(
        identity, facts, rules, history, events
    )

如果 load_*() 涉及磁盘读取、SQLite 查询或复杂排序，那么锁持有时间可能很长。

主线程写记忆时就可能等待，其他读取任务也可能被阻塞。

更合理的方式是：

在明确的同步边界上获取需要的数据。
将数据复制成不可变快照。
释放锁。
在锁外执行排序、去重、字符预算计算和上下文拼接。

不过，简单地对每个字段分别加锁也有问题：身份、事实、家规和历史记录可能来自不同的时间点。

所以你需要先确定一致性要求。

对于第一版，我建议接受有界的最终一致性，而不是为了所有记忆类型都获得严格的跨存储事务而引入复杂分布式协调。

例如，上下文构建可以基于一个有明确版本号或读取时刻的快照；如果暂时无法做到跨 SQLite 和 JSONL 的统一快照，至少要明确其一致性边界，并确保上下文不会包含半条记录或无效对象。

5.3 JSONL 的追加写入需要故障恢复策略

你的声音记忆和情景记忆采用 JSONL 是合理的，但追加写入并不意味着文件天然安全。

可能出现：

进程被强制终止，最后一条记录只写了一部分。
多个线程同时写入，记录发生交错。
磁盘空间不足。
编码异常。
写入成功返回，但数据尚未持久化到物理介质。
长时间运行后，文件过大，启动恢复和查询越来越慢。

建议：

让一个专用写入器负责每个 JSONL 文件。
将每条记录序列化为完整的一行。
启动时验证最后一条记录，并对不完整尾记录进行明确的恢复处理。
区分普通 flush() 与需要更强持久性保证的 fsync()。
定期轮转或分片，避免单个文件无限增长。
记录写入失败，并定义磁盘空间不足时的降级策略。

如果语音记忆涉及声纹嵌入，不要把高维向量随意转换成 JSON 浮点数后无限追加。这样既会放大存储体积，也会增加解析成本。可以考虑独立的向量存储文件、SQLite BLOB 或其他适合二进制数据的格式，并在 JSONL 中保留索引与元数据。

6. 五类记忆的分类合理，但生命周期需要重新审视

你现在的五类记忆是：

类型	存储方式	评审意见
Voice	JSONL	可行，但声纹与对话文本最好有明确的权限边界
Working	进程内 TTL 环形结构	适合短期状态，但重启后会丢失
Semantic	SQLite 键值事实	合理，但需要事实来源、更新时间与冲突规则
Episodic	JSONL 事件流	合理，但需要轮转、恢复与保留策略
Procedural	JSON 技能/家规	合理，但需要版本、校验和安全更新机制

真正的问题不是五种存储格式是否正确，而是五类记忆之间缺少明确的数据生命周期和更新契约。

例如：

纯文本
用户说：“我现在住在武汉。”
          │
          ▼
       ASR 转写
          │
          ▼
       情景记忆
          │
          ▼
       事实提取
          │
          ▼
       语义记忆

如果语义记忆立即将这句话作为永久事实写入，后续用户说“我下个月要搬去上海”，系统就需要判断这是计划、当前状态，还是对旧事实的修正。

建议语义事实至少包含：

Python
{
    "key": "user.current_city",
    "value": "武汉",
    "source_event_id": "...",
    "confidence": 0.92,
    "valid_from": "...",
    "valid_until": None,
    "updated_at": "...",
}

这只是一个示例 Schema。

还应根据实际需求添加事实来源、用户确认状态和冲突处理规则。对于“可能住在某城市”这样的推断，不应与用户明确确认的事实拥有相同的可信度。

6.1 你需要一个重要的记忆规则：可撤销、可过期、可追溯
Working Memory：TTL 到期自动清理。
Semantic Memory：允许更新、撤销和标记过期。
Episodic Memory：追加事件时保留事件来源与时间。
Procedural Memory：更新前验证格式与版本，失败时回退。
Voice Memory：支持删除、重新注册、禁用和保留期限。

特别是声纹数据，建议将原始录音、嵌入、身份映射和对话文本视为不同的数据对象，分别定义保存期限、访问权限与删除行为。

7. 字符预算合理，但不能把字符数当成模型 Token 数

你当前的上下文构建规则：

身份 → 事实 → 家规 → 最近轮次 → 最近事件；超预算的块整块丢弃，不截断。

这个设计有一个优点：不会把重要的结构化事实截断成残缺内容。

但也有两个需要注意的问题。

第一，字符预算不等于 Token 预算。

中文、英文、代码、JSON 和特殊符号的 Token 化效率不同。固定 4000 个字符，并不意味着固定数量的模型 Token。

如果你的 LLM 后端提供 tokenizer，建议优先按 Token 预算计算；如果不希望运行时依赖 tokenizer，则采用保守的字符预算，并为系统提示词、当前用户输入、模型输出预留空间。

第二，整块丢弃可能导致关键事实被挤掉。

例如：

纯文本
身份信息：200 字
重要家规：300 字
最近 10 轮对话：3000 字
旧事件：1500 字

如果超预算后只是从上到下逐块拼接，可能出现某些重要信息始终被保留，而与当前任务直接相关的事实却被丢弃的情况。

建议保留你的结构化分块方式，但将优先级与相关性分开：

必须保留的系统约束。
当前用户请求。
身份与关键事实。
与当前任务相关的程序记忆。
最近几轮对话。
相关情景事件。
其他低优先级历史信息。

每个块都应该有明确的优先级、相关性评分和最大预算。

对某个块而言，如果整块丢弃会导致系统无法正确回答，就应该优先保留或返回明确的上下文不足状态，而不是静默丢弃。

四、P1：24 小时长跑，真正容易出问题的地方

你已经设计了 max_seconds、max_turns、idle_timeout_s、worker_timeout_s、maintenance_interval_s 和信号处理。这是好的起点，但这些参数覆盖的是不同层次的问题，不能互相替代。

它们不一定都需要暴露为公开配置，但系统内部必须有相应的故障检测机制。

8.1 监听循环需要心跳

假设系统启动了 24 小时任务，但音频采集设备在运行 3 小时后断开。

如果主循环只检查：

Python
while not shutdown_requested:
    ...

那么它可能一直运行，却再也收不到音频。

建议维护以下心跳：

最近一次成功采集音频的时间。
最近一次 VAD 成功处理的时间。
最近一次播放进度更新的时间。
最近一次后端请求完成的时间。
最近一次记忆写入成功的时间。

如果某个组件超过合理时间没有进展，应触发健康检查和恢复流程，而不是让主循环无限等待。

注意：空闲与卡死必须区分。长时间没有用户说话可以是正常空闲，但音频采集心跳停止通常不是正常空闲。

9. 音频设备断开与恢复，需要单独设计

你已经发现当前机器没有可用麦克风，而且本机的 torch 是 CPU-only。

这实际上说明你的开发环境需要明确区分：

不存在音频设备。
存在音频设备，但初始化失败。
设备运行过程中断开。
设备仍然连接，但没有有效输入。
设备可以采集，但输出设备不可用。

不要将这些情况全部处理成 AudioSource.read() 返回空数据。

建议定义清晰的接口：

Python
class AudioSource(Protocol):
    def open(self) -> None: ...
    def read(self, timeout_s: float) -> "AudioFrame": ...
    def healthcheck(self) -> "HealthStatus": ...
    def close(self) -> None: ...

这里的 AudioFrame 应包含采样率、时间戳、通道信息及必要的格式元数据。

对于设备错误，建议明确区分：

暂时没有音频数据。
正常静音。
设备已断开。
设备读取超时。
采集后端出现不可恢复错误。

对于暂时断开的设备，可以按退避策略重新初始化；但必须限制重试频率，并记录每次失败原因。

如果没有可用麦克风，系统应进入明确的 NO_AUDIO_DEVICE 或降级状态，而不是假装自己正在正常监听。

10. 周期维护不能与实时音频链路抢资源

你设计了：

Python
maintenance_interval_s = ...

但还需要明确维护任务执行哪些操作。

如果维护任务会同时做以下事情：

扫描整个 JSONL 文件。
重新加载所有情景事件。
清理大量过期记忆。
重建索引。
执行 SQLite 大事务。

那么维护期间就可能出现明显的音频处理延迟。

建议：

维护任务独立调度。
使用增量清理，而不是每次扫描全部数据。
为每次维护设置处理数量或时间预算。
将耗时维护安排在系统相对空闲时。
对 SQLite 写事务设置合理的边界。
监控维护开始前后队列积压和音频延迟。

尤其不要让记忆清理和磁盘 I/O 直接发生在音频采集回调中。

11. 优雅退出不等于调用 flush() 就完成了

你提到收到 SIGTERM 或 SIGINT 后：

停 sink、flush 记忆、关 source。

这个顺序还需要细化。

一个容易出现的错误是：先关闭音频资源，再等待工作线程结束，而工作线程还在向播放队列写入数据。

另一个错误是：退出时仍有后台任务继续写 JSONL，导致主线程已经退出，但文件还在被修改。

建议将关闭流程设计成有界的状态机：

纯文本
RUNNING
   │
   ▼
QUIESCING
   │
   ├── 停止接收新任务
   ├── 停止接受新的播放数据
   └── 发出当前任务取消信号
   │
   ▼
DRAINING
   │
   ├── 等待可控任务结束
   ├── 清理或取消未播放音频
   └── 排空必要的记忆写入队列
   │
   ▼
CLOSING
   │
   ├── 关闭音频输入与输出
   ├── 关闭数据库连接
   ├── 关闭文件写入器
   └── 释放其他资源
   │
   ▼
STOPPED

需要注意，退出时并非所有任务都应该等待完成。例如，正在进行的 LLM 请求如果已超过退出期限，就不应无限等待。

因此应该设置 shutdown_grace_period_s，到达期限后按预先定义的策略结束。

对于需要保存的记忆，建议采用专用写入队列，并明确退出时哪些记录必须持久化，哪些允许丢弃。

另外，信号处理函数本身应尽量轻量：设置退出标志、唤醒协调器即可。不要在信号处理函数中执行复杂的数据库事务或音频设备关闭操作。

这里我尤其强调三个问题。

第一，不能无限重试。 如果 ASR 服务已经不可用，系统不应该每隔几毫秒重新发起请求。使用指数退避、最大重试次数以及熔断恢复探测。

第二，不能无限积压。 24 小时运行的系统必须定义过载行为。对过期的打断任务结果，直接丢弃通常比排队等待更合理。

第三，不能只看进程是否存活。 一个进程可以一直运行，但采集线程已经死掉、播放队列已经卡住，或者所有 Worker 都被阻塞了。健康状态应该反映业务链路是否仍在推进。

14. Protocol 不仅要定义接口，还要定义行为契约

你为 ASR、TTS、LLM、声纹嵌入分别定义 Protocol，这个方向是对的。

但如果不同后端对取消、超时、数据格式和错误的理解不同，那么统一接口只是表面上的统一。

例如，TTS 接口如果只有：

Python
def synthesize(text: str) -> np.ndarray:
    ...

那么调用方无法知道：

音频采样率是多少。
输出是单声道还是双声道。
数据是 float32 还是 int16。
是否支持流式生成。
是否支持取消。
是否可能返回空音频。
失败时会抛出哪些异常。

建议把这些契约明确下来。

例如：

Python
@dataclass(frozen=True)
class AudioBuffer:
    samples: np.ndarray
    sample_rate: int
    channels: int

然后为 TTS 进一步定义流式输出接口和取消语义。

同样，ASR 的输入也应明确采样率、通道数、音频长度以及是否已经完成分段。

对于 HTTP 后端，还应该统一处理：

连接失败。
超时。
服务器错误。
请求被取消。
返回内容格式错误。
服务端限流。

这些错误可以归一化为核心层能够理解的异常类别，但不应把所有错误都转换成空字符串或空音频。

否则，Agent 可能把后端故障误认为用户没有说话。

15. 四类 Backend 的设计有价值，但测试不能止步于 Mock

你的四种实现：

http
transformers
scripted
mock

是有价值的，尤其适合在没有麦克风或本地模型资源有限时开发。

但需要区分三种不同的测试目标。

测试层级	使用什么	能验证什么
单元测试	Mock	状态转换、异常分支、取消逻辑
确定性集成测试	Scripted	多轮交互、打断时序、记忆更新
真实后端测试	HTTP / Transformers	网络行为、模型输出、延迟和资源使用

Mock 能验证你的控制逻辑，却无法证明真实后端可以被取消。

例如，Mock 的 TTS 可以在收到取消事件后立即返回，但真实 TTS 服务可能仍然阻塞几十秒。

因此，建议为每个 Backend Protocol 定义一套共享契约测试。

每种实现都至少测试：

正常输入输出。
非法输入。
空结果。
后端超时。
主动取消。
连续失败后的恢复。
资源关闭。
重复调用。
返回格式异常。
运行中途关闭服务。

对于支持流式输出的后端，还应测试生成中途取消、部分结果返回以及取消后是否仍然产生输出。

六、P1：声纹识别与声音记忆
16. Log-mel 统计池化适合做占位实现，不适合直接当作可靠声纹识别器

你已经意识到这一点。

Log-mel 特征描述的是语音的频谱特征，统计池化则可以把不同长度的语音片段压缩成固定维度的向量。

这种表示可以用于原型开发，但它同时会受到以下因素影响：

说话内容。
录音设备。
距离与混响。
背景噪声。
音量与语速。
音素分布。
说话状态变化。

因此，同一个人说不同的句子，得到的向量可能出现较大差异；不同的人也可能得到相似的向量。

你可以继续保留 mel Backend，但建议明确标记：

纯文本
mel_backend:
    capability = "feature_baseline"
    identity_verification = "unsupported"

这样可以避免其他模块误以为它已经实现可靠的身份识别。

真正的声纹系统通常需要经过说话人验证训练的嵌入模型，以及相应的相似度评分、阈值校准和质量控制。

16.1 声纹匹配不能只看余弦相似度

即使换成了真实的 Speaker Embedding 模型，也不能直接认为：

Python
same_person = cosine_similarity(a, b) > 0.8

就是可靠的身份验证。

阈值需要结合模型、录音条件和目标误识率进行验证。还应处理过短音频、低信噪比、静音和多人重叠说话等情况。

建议增加：

最短有效语音时长。
语音质量检查。
未知说话人拒识。
多次采样后的身份一致性判断。
身份匹配的置信度和阈值校准。
说话人注册与重新注册机制。

如果声纹识别会影响访问权限或敏感操作，就不能把它当成唯一的身份认证手段。 声纹验证可能受到录音重放、合成语音和模仿攻击影响。

对于普通个人助理，可以将它用作个性化上下文选择；对于安全敏感的操作，则应采用额外的授权机制。

七、P2：语音切分与用户输入完整性
17. “VAD 检测到一句话结束”不等于获得了一句完整的话

你的设计以 VAD 闭合事件启动 ASR，这是一种常见的架构。

但 VAD 只能判断语音活动区间，不能可靠地确定语言学意义上的句子边界。

例如：

用户：我觉得这个项目最大的问题是……

用户停顿了 700 ms。

VAD 可能判断这句话已经结束，但用户实际上还没有说完。

反过来，如果用户说话很快，中间没有明显静音，VAD 可能把多句话合并成一个片段。

建议区分三个时间参数
Python
vad_start_threshold
vad_end_silence_ms
max_utterance_duration_s

同时维护：

前置缓冲区。
当前语音段缓冲区。
尾部静音缓冲区。
当前分段的起止时间戳。
最大录音长度。
段间合并与拆分策略。

前置缓冲尤其重要：VAD 通常需要观察到若干帧语音后才能确认开始。如果直接丢弃触发前的音频，可能会丢失用户说话的第一个音节。

打断期间的音频必须保留

你提到：

把触发打断的这一帧当作新话的开头。

这个想法是对的，但只保留触发帧还不够。

假设 VAD 需要连续 3 帧确认语音，每帧 20 ms。

在确认打断之前，用户已经说了约 60 ms 的内容。如果前两帧只被用于打断判决，却没有进入新语音段，那么 ASR 可能丢失这部分开头。

建议在持续监听时保留一个短前置环形缓冲区。

当 VAD 确认开始新语音段时，将触发前的有效音频一并纳入分段缓冲区。

这也适用于普通的语音起始检测，而不仅仅是 Agent 正在播放时的打断。

八、P2：24 小时运行的观测与测试体系
18. 没有可观测性，就无法判断系统是否真的稳定

建议为 qwen-voice-agent 建立一套独立的运行指标。

指标	用途
capture_frame_age_ms	判断输入音频是否积压
vad_processing_ms	监控语音检测耗时
utterance_duration_s	观察语音切分是否异常
asr_latency_ms	监控 ASR 响应时间
llm_ttft_ms	监控首个文本 Token 延迟

playback_buffer_ms	观察播放缓冲区积压

barge_in_stop_ms	测量从插话到实际停止播放的时间
stale_result_discard_total	统计被丢弃的旧任务结果
queue_depth	监控各队列积压

注意区分两个关键延迟：

打断检测延迟： 用户开始说话到系统确认用户正在插话。

第二个指标更能体现用户实际感受到的全双工体验。

纯文本

    =
语音检测延迟
    + 调度延迟
    + 播放停止延迟

这是便于定位问题的近似分解。真实系统中还存在音频设备缓冲、采集与播放时钟差异等因素。

19. 测试重点应该从“能运行”转向“故障后还能恢复”

我建议将测试分成四组。

A. 全双工功能测试

Agent 说话时用户插话。
Agent 还在生成文本时用户插话。

Agent 播放时出现回声。
用户与 Agent 同时说话。
旧任务在新任务启动后才返回。

B. 长时间稳定性测试

连续运行 24 小时。
每隔一段时间触发打断。
周期性制造 HTTP 超时。
模拟音频设备断开和恢复。
运行过程中触发记忆维护。
反复创建和销毁对话任务。
持续监控 RSS、线程数、队列深度和文件描述符。

C. 持久化故障测试

写入 JSONL 中途终止进程。
SQLite 事务执行时关闭进程。
模拟磁盘空间不足。
模拟记忆文件损坏。
在维护与普通读写并发时进行压力测试。

D. 取消与恢复测试

每个后端在不同阶段收到取消信号。
旧请求超时后，新请求仍然能够执行。
Worker 抛出异常后，系统恢复到可监听状态。
播放停止失败后，系统能够报告故障，而不是假装已停止。
退出过程中，正在写入的记忆能够按既定策略完成或明确失败。

对于时间相关的测试，建议使用可控时钟或注入式时钟接口，避免所有单元测试都依赖真实的 sleep()。

十一、最后给出几个明确判断
哪些设计是对的？

1. 纯 NumPy 核心：保留。

它让你可以在没有音频设备、没有 GPU 推理环境的机器上测试核心逻辑。只需要明确哪些能力是核心能力，哪些属于可选后端。

2. Backend Protocol：保留。

但必须将超时、取消、错误类型和音频数据格式纳入契约，而不仅仅是统一函数签名。

3. Mock / Scripted 后端：保留。

它们对于确定性测试非常重要，尤其适合测试打断、任务取消和记忆竞态。但不能用 Mock 测试结果代替真实后端的取消验证。

4. 五类记忆：保留。

你的分类足以支撑第一版系统。现阶段应优先解决数据生命周期、写入一致性和检索质量，而不是继续增加记忆类型。

5. 限时运行、优雅退出和周期维护：保留。

但要补充健康检查、设备恢复、磁盘故障处理以及退出期限。

哪些地方需要调整？

第一，全双工必须由独立的音频输出控制器保障，而不能只依赖 Worker 的取消标志。

第二，VAD 只是打断检测的一部分，必须考虑回声、双讲和前置音频保留。

第三，Python 线程不能被 Event 强制终止，必须为阻塞调用提供实际可执行的超时或取消方案。

第四，记忆并发安全要通过明确的资源所有权、事务边界和快照语义来实现，而不是简单地在所有地方加锁。

第五，24 小时稳定性必须通过故障注入和长时间测试验证，而不是通过配置项的存在来推断。

建议你先实现的三个验收实验

如果当前项目还处于架构实现阶段，我建议先不要同时开发所有后端和五类记忆。先完成下面三个实验。

实验 A：打断正确性

使用确定性的 Scripted TTS 生成一段较长音频，在播放过程中模拟用户插话。验证：

系统能够检测插话。
播放设备真正停止输出旧任务的声音。
插话音频开头没有丢失。
新一轮对话能够开始。
旧任务即使迟到返回，也不会污染新一轮。

实验 B：阻塞后端恢复

让 Mock 或 Scripted 后端模拟永久阻塞、延迟返回、超时和异常。验证：

主音频采集路径不受阻塞。
超时后不会无限累积 Worker。
新任务仍然能够执行。
系统状态能够恢复到可监听状态。

实验 C：24 小时故障注入

连续运行整个系统，周期性触发打断、模拟后端超时、执行记忆维护，并监控内存、线程数、队列深度和音频延迟。中途模拟音频设备断开，观察系统能否进入明确的降级状态并恢复。

这三个实验比一开始就接入所有真实模型更有价值，因为它们验证的是整个项目最难修复的基础设施问题。

最终评审意见：保留你的核心模块划分，但先把任务生命周期、实时音频控制、取消语义和故障恢复做扎实。 对一个需要连续运行 24 小时、支持用户随时插话的语音智能体来说，这些基础设施的正确性，比先接入更大的 LLM 或更复杂的记忆系统更重要。
